# divergence チェックポイントと探索（Issue #774、設計）

**ステータス:** 設計のみ。このドキュメントの内容はまだ実装されていません。実装は Phase B-6 以降です。

**関連 Issue:** #774

**関連コンポーネント:** `UnitTraceJoiner` とユニットトレース（[unit-trace.ja.md](unit-trace.ja.md)）、`RecompilerHostCodeGen`（native の state struct）、`InterpreterTitleExecutionEngine`（`RunLoop`、`RunFallbackSegment`）、`FrameSnapshot` / `CaptureFrame`（Issue #575）

[English (Canonical / SSOT)](divergence-checkpoints.md)

## 目的

Phase C では、純粋なインタプリタと生成された native ホストが、standalone の表示経路で最初に一致しなくなる地点を探し、その後でそれを引き起こした命令を特定する必要があります。このドキュメントは、その測定を始める前に次の 3 点を定めます。

1. 両者をどの地点で比較できるか。
2. チェックポイントに何を記録し、各側がどう生成するか。
3. 実行全体から 1 命令まで探索を絞り込む方法と、Phase C をいつ開始してよいか。

## 1. 比較可能な境界

アーキテクチャ状態を比較できるのは、clean な境界だけです。候補は次のとおりです。

| 境界 | native 側 | インタプリタ側 | clean である理由 |
|---|---|---|---|
| native unit の終端 | unit の epilogue | `RunLoop` のステップ終端 | unit は分岐と delay slot の融合なので、境界をまたぐ delay slot 状態がない。 |
| handoff | ホストへの transfer | `RunFallbackSegment` の入口 | native コードは transfer の前に状態を artifact へ書き戻している。 |
| fallback の return | `returned` 区間、`WriteBack` 完了後 | `returnPcs` の判定 | return 判定は `IsPipelineClean` を要求する。delay slot の保留も未確定の load もない。 |
| 割り込みの entry | ベクタへのリダイレクト | `ExceptionRaised` を伴う `Step` | CPU が定める境界だが、割り込まれた fetch は retire していない（トレースのドキュメント参照）。 |

両側は、両方がその地点に境界を持つ場合にのみ、同じ **global retirement 位置** `g` で比較されます。結合トレースの区間の終端がその位置を与えます。融合 unit の内部、割り込みのリダイレクトの内部、fallback 区間の内部では、何も比較しません。

`g` が一致するだけでは不十分です。チェックポイントは、境界の種類、PC、delay slot の保留状態（これらの境界では常に 0。0 以外はそれ自体が不一致）、割り込みハンドラの状態も一致する必要があります。

### retirement の定義（B-6a）

命令が **retire** するのは、完了して、その architectural な効果が後続の命令から見えるときです。すなわち、PC がプログラム順の次の命令か分岐先へ進むときです。次の場合は retire しません。

- 実行前に割り込みで fetch を先取りされた命令。
- 処理されない例外を起こした命令（実行が止まるか、ハンドラへ飛ぶ）。
- 例外の entry 自体。

**処理済み SYSCALL は retire します。** デバイス時間を 1 単位消費し、後続の命令から再開します。したがって、この計数は fetch（先取りされた fetch を含む）やスケジューラの単位（処理済み SYSCALL も含む）とは別のものです。遅延スロットでの例外は未決の事例です。現状では両エンジンとも分岐を計上しますが、R3000 の再開モデルでは分岐は再実行されます（トレースのドキュメント参照）。

### 例外・割り込み時の PC 表現（B-6a）

PC の値は互いに別物であり、単一の PC として比較してはなりません。次の表は、現在の両側が実際に観測できるものを示します。

| フィールド | 意味 | native（生成ホスト） | インタプリタ / fallback |
|---|---|---|---|
| `executed_pc` | unit または区間が最初に実行した命令の PC | `entry`（割り込み境界の後に記録） | 最初のステップの fetch PC |
| `architectural_next_pc` | 最後に retire した命令の後続の PC | 正常終了時の `next` | 正常な return 時の `end_pc` |
| `transfer_target_pc` | ホストへの transfer の対象の PC | `handoff.pc` | transfer レコードの `start_pc` |
| `exception_vector_pc` | 例外・割り込みで入ったベクタ | ハンドラのレコードの `entry`、または 0x80000080 の `handoff.pc` | 割り込み後の `end_pc` |
| `interrupted_pc`（先取りされた fetch） | 割り込みが実行前に止めた命令 | **記録されない**（最後に完了した PC は `entry` と retired から得られる） | **記録されない**（fetch はされるが保存されない） |
| `retired_before_exception` | 例外の前に完了した命令数 | unit の `retired` | 区間の `retired` |
| 例外・割り込みの種類 | 何が起きたか | `exception` フラグと `termination` | `stop` コードと termination |

B-6a で確認した内容: unit 内部の割り込みでは `entry` が実行された PC、`retired` が 1、`next` がベクタを記録します。先取りされた PC は保存されないため、インタプリタの fetch の列からのみ復元できます。`interrupted_pc` を明示的に記録する提案には、両側に追加的なフィールドが必要です（B-6b）。それまでは保存されず、利用側は推測してはなりません。

## 2. CPU チェックポイント

チェックポイントは 1 件につき JSON Lines の 1 レコードで、両側が同じ schema で書きます。

| フィールド | 内容 | 取得元（native / インタプリタ） |
|---|---|---|
| `g` | global retired 位置 | 結合トレース / `retired` カウンタ |
| `kind` | `unit_end`、`handoff`、`fallback_return`、`interrupt_entry` | 上記の境界 |
| `pc`、`next_pc` | 境界での PC | `pc`、`next_pc` / `_core.Pc` |
| `gpr[32]`、`hi`、`lo` | 汎用レジスタと乗除算レジスタ | state struct / `ReadGpr()`、`Hi`、`Lo` |
| `sr`、`cause`、`epc` | COP0 制御レジスタ | `cop0_sr`、`cop0_cause`、`cop0_epc` / `GetCop0` |
| `handler` | ハンドラ内フラグ、RFE 保留フラグ、ハンドラの EPC | state / `_inInterruptHandler`、`_rfePending`、`_handlerEpc` |
| `load_pending` | 未確定の load が存在する | state / `IsPipelineClean` |
| `time` | デバイスのスケジューラ時刻 | `event_deadline` と `retired_total` / `_scheduler` |
| `mem` | 選択した RAM 範囲のハッシュ（3 節） | 両側、同じ範囲 |

native の state struct にはすでに COP0 のフィールド（`cop0_sr`、`cop0_cause`、`cop0_epc`、`cop0_other[32]`）があるため、その側では新たな保存領域は不要です。これらの値が handoff だけでなく全 unit 境界で最新か否かは、B-6 で確認します。

**上限。** チェックポイントは、ユニットトレースと同じ上限と切り詰めの規則に従います（既定 64 MiB、上限到達時は `truncated` と `complete:false`）。これにより、実行がファイルを無制限に大きくすることはありません。

## 3. メモリ

- **選択した範囲。** 比較は、調査ごとに指定された名前付きの RAM 範囲を対象とします（例: カーネルのデータ領域、実行ファイルのデータ区間、スタック）。既定では RAM 全体は対象にしません。
- **ハッシュ。** 各範囲を、各チェックポイントでハッシュします（一度の実行内での一致判定には 64 ビット FNV-1a で十分）。最初の不一致では、直前の一致したチェックポイントと不一致のチェックポイントで、その範囲のバイト列を読み、変化したワードを特定します。読み取りは範囲の大きさで上限が決まります。
- **変更領域の追跡**（store の経路で更新するダーティページのビットマップ）は選択肢であり、必須ではありません。native の store 経路に触れるため、選択した範囲の全ハッシュが遅すぎると分かった場合にのみ、B-6 で判断します。
- **DMA とデバイスの書き込み**は命令ではありません。`g` と `time` を付けたデバイスイベントとして、両側が同じデバイスコードから生成する別のログに記録します。状態としてではなく、列として比較します。
- **禁止事項:** 命令ごとの RAM 全体のハッシュ、命令数だけに依存する比較。

## 4. 表示

表示状態が最終的な比較対象です（Issue #774 は standalone の表示の divergence です）。ただし、CPU の位置の関数ではありません。

- **VRAM ハッシュ。** VRAM 全体（1024 × 512 × 16 bit）は、VBlank の境界でのみハッシュします。既存の probe は VRAM を 15 bit として読むため、黒いフレームは VRAM が黒いことの証拠ではありません。VRAM のハッシュは GPU 状態の一致であり、描画画像の一致ではありません。
- **選択した領域。** 表示領域と描画領域は、同じ VRAM の読み取り経路を使って別々にハッシュします。
- **GPU コマンドの進行。** GPU のコマンドキューは CPU の命令数では空になりません。各チェックポイントは、キューの深さと最後のコマンド番号を記録します。両方のキューが空のときにのみ VRAM を比較します。そうでない場合、チェックポイントは `gpu_busy` と印を付けられ、比較されません。
- **フレームの取得。** `CaptureFrame`（Issue #575）は現在の表示状態を取ります。フレームは CPU の位置ではなく、デバイスのスケジューラ時計上の VBlank 割り込みで比較します。
- **同期。** CPU のチェックポイントと表示のチェックポイントは、スケジューラの `time` が同じ場合にのみ対にします。CPU のチェックポイントは、VBlank イベント時刻以降で最初の clean な境界です。両側とも命令の実行ごとにデバイス時間を消費するため（処理済み SYSCALL は両側とも 1 単位。デバイス時間の契約テスト参照）、retirement 数が異なっていても `time` の値は一致します。

## 5. divergence の探索

各段階は探索範囲を絞り込み、その結果は次の段階に進む前に記録します。

**レベル 1: チェックポイント比較。** `g` の順にチェックポイントを走査し、両側にチェックポイントがある位置だけを比較します。最後に一致したチェックポイント `k-1` と、最初に不一致となった `k` を報告します。`Partial` の結合トレース（`ComparableUpToRetired`）や `Rejected` の結合を超える部分は比較しません。

**レベル 2: unit レベルのトレース。** 区間 `(k-1, k]` を、結合区間に対応づけます。開始は一致し、終端は一致しない最初の区間を探します。その出所（native unit、fallback 区間、host transfer）、entry と next の PC、retire 数を報告します。検証済みの区間だけを使います。

**レベル 3: 命令レベルのトレース。** レベル 2 で見つけた 1 区間についてのみ、命令ごとの記録を有効にします（各ステップでのインタプリタの fetch、レジスタ、PC。native 側には命令レベルのフックが必要で、これは B-6 の作業です）。窓は `g` と、レコード数の上限で区切ります。実行全体を命令レベルで記録することはありません。

**レベル 4: 根本原因。** 最初に異なるフィールド（レジスタ、RAM のワード、デバイスイベント）から出発し、窓の中でそれを書いた命令を探します。そして、その命令に至った制御転送やデバイスの更新を特定します。最初に観測された不一致と根本原因を別々に報告します。原因より後に観測された不一致は、原因ではありません。

## 6. 既知の阻害要因

以下は Phase C を阻害します。B-5 では修正せず、ここに記録します。

1. **処理済み SYSCALL の計上が一致しない。** native コードで処理された SYSCALL は 1 回計上され、fallback で処理された同じ SYSCALL は計上されません。両側ともデバイス時間は 1 単位ずつ進むため、`time` は一致し、グローバルな retirement の位置だけが片側で 1 ずれます。判定（B-6a）: 処理済み SYSCALL は retire した命令とみなします。欠陥はインタプリタ側の計上です。修正は報告用の計上の変更で、#789 で扱います。固定化したテストは `KnownDivergence_ServicedSyscallInTheFallback_IsFetchedButNotRetired` で、現在の値を検証しています。
2. **割り込み後の `next` の位置。** fallback 区間内の割り込みでは `end_pc` はベクタで、割り込まれた PC は記録されません。native の unit 内部での割り込み（B-6a で再現）でも `next` はベクタです。一方、native の unit 境界での割り込みでは `next` はプログラム順の PC のままで、transfer レコードがベクタを持ちます。チェックポイントは `kind = interrupt_entry` を用い、これらの場合に `next` を比較してはなりません。
3. **融合 unit の部分完了と native 内部の割り込みは再現済み（B-6a）。** 融合したロードのブロックの 2 命令の間にタイマーの立ち上がりが来ると、`interrupted` の unit が retired 1 と、ベクタを指す `next` を持ちます。チェックポイントの規則はテスト可能になりましたが、規則そのものは未実装です。

## 7. Phase C のゲート

Phase C（実際の standalone 経路での最初の divergence の測定）は、次のすべてが成り立つ場合にのみ開始できます。右欄は B-5 終了時点の状態です。

| 条件 | B-5 終了時点の状態 |
|---|---|
| 処理済み SYSCALL の計上が両側で一致する、または明示的な対応づけが記録され、テストされている | 未達（修正案あり、未適用。欠陥はインタプリタ側の計上と判定。阻害要因 1） |
| CPU 状態と選択した RAM について、チェックポイント形式が両側に実装され、合成プログラムで同じ位置に誤った不一致が出ない | 未達（設計のみ） |
| 割り込み entry の規則（阻害要因 2）が実装され、テストされている | 未達（文書化のみで未実装） |
| VRAM の比較が、VBlank でのみ、かつ GPU キューが空のときにのみ実行される | 未達（設計のみ） |
| 融合 unit の部分完了と native 内部の割り込みの場合が再現されている、または生成コードに存在しないことが示されている | 再現済み（B-6a）。規則そのものは未実装 |

Phase C はまだ開始できません。
