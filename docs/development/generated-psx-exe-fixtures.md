# Source-generated PS-X EXE fixtures

**Status:** Stable

**Authority:** Reference

**Related Issues:** #606, #461

**Related Components:** `src/PSXRecomp.Tests/E2E/GeneratedPsxExeFixtures.cs`, `src/PSXRecomp.Tests/E2E/RecompiledArtifactE2ETests.cs`

## Purpose

The generated-fixture suite is the reproducible evidence layer between small
unit tests and user-supplied real PS1 inputs.

A fixture is a tiny PS-X EXE generated in memory from repository-authored MIPS
instruction words. The generated bytes run through the same production parser,
input bridge, lowering, code generation, artifact build, and runtime path used
by the existing E2E tests where that path is applicable.

No generated `.exe` file is checked into the repository.

## Legal and ownership boundary

The fixture source contains only:

- repository-authored test instruction words;
- the documented PS-X EXE interoperability header fields required by the parser;
- expected machine-readable evidence such as result values, guest PCs,
  diagnostic codes, and SHA-256 values.

It does **not** contain or derive from:

- commercial game executables or disc images;
- Sony BIOS code or BIOS images;
- extracted title data, assets, tables, or executable fragments;
- user-provided real-input fixtures.

The source is ordinary repository test code and follows the repository license.
User-supplied real PS-X EXEs remain under the separate `RealExeFixtures`
mechanism and are never promoted into this catalog.

## Current fixtures

| ID | Contract | Expected evidence |
|---|---|---|
| `bios-putchar-marker` | production BIOS-HLE A0 putchar call plus normal program-end handoff | completed/success, S1 = `0x7777`, TTY byte `P` |
| `unresolved-jump` | MIPS jump + delay slot leaves the compiled image | blocked/unsupported-transfer, guest PC `0x80020000`, `UNRESOLVED_TRANSFER` |

Each fixture also carries the expected SHA-256 of the complete generated PS-X
EXE. This pins the generated bytes independently of "generate twice and compare"
tests: a deterministic but unintended format/instruction change still requires
an explicit expected-hash update and review.

## Generation contract

`GeneratedPsxExeFixtures.BuildExe` constructs a minimal PS-X EXE entirely in
memory:

1. writes the `PS-X EXE` magic;
2. writes entry point, GP, text address/size, and SP fields;
3. writes instruction words explicitly as little-endian values;
4. returns the byte array to the production `PsxExe.Load` parser.

The helper intentionally does not write the generated image to the source tree
or create a second parser/runtime.

## Verification

`GeneratedPsxExeFixtureTests` proves:

- the catalog has multiple unique, inspectable fixtures;
- repeated generation is byte-identical;
- each image matches its pinned SHA-256;
- the production `PsxExe.Load` parser recovers the exact header/instruction
  data.

`RecompiledArtifactE2ETests` then consumes catalog fixtures through the
production recompiler/runtime path and checks their declared evidence.

These tests require no ROM or BIOS asset, so they run in normal CI.

## Adding a fixture

1. Choose one bounded architecture/runtime behavior with a machine-verifiable
   expected result.
2. Add only the minimal repository-authored instruction sequence to
   `GeneratedPsxExeFixtures`.
3. Give it a stable lowercase/hyphenated ID and a short contract description.
4. Generate the image with `BuildExe`; do **not** commit the resulting binary.
5. Compute and pin the expected SHA-256.
6. Add the fixture to `All`.
7. Add or extend a production-path test that consumes the fixture and asserts
   its declared state/outcome plus the behavior-specific evidence.
8. Run the generated-fixture tests and the relevant production-path E2E tests.
9. Treat a pinned-hash change as a deliberate fixture-contract change and
   explain it in the PR.

A fixture should stay small enough that its instruction words and expected
behavior can be reviewed directly. If reproducing the case requires commercial
content or a large software stack, it belongs in the legal real-input evidence
layer instead.

## Non-goals

- A PS1 homebrew SDK or assembler.
- Replacing commercial-title/Persona verification.
- Committing generated executable artifacts.
- Emulating unsupported behavior inside test helpers.
- Creating title-specific workarounds.
