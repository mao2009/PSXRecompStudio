### 2.6 Environment variables

Scope: `git grep -nE 'GetEnvironmentVariable|getenv' -- src ':(exclude)src/PSXRecomp.Tests'` returns 19 matching lines in 8 files (CONFIRMED). Those lines include the `PATH` read (`src/PSXRecomp.Cli/PackageCommand.cs:421`), which is in the table. The table covers every variable on those lines, plus the child-process writes the engine makes for the same keys.

Column meanings:

- **Build or run**: "build" means the variable is read while packaging or code generation decides what an artifact contains. "run" means it is read when a process runs.
- **In packaged artifact**: whether the generated C that a distribution ships can contain the read.
- **Proposed production action (not implemented)**: "Refused" means packaging would reject the build flag that enables the read. "Not refusable" means the read is in shared host code that packaging does not generate, so packaging cannot remove it. For those, the design only forbids a launcher from setting the variable.

## 3. Shared runtime configuration schema (proposal)

### 3.1 Two tiers, and what the packaged host reads

The schema separates two kinds of value, because they have different lifetimes and different readers:

1. **Execution settings (frozen at package time).** Values that change what the guest runs or how long it may run: budgets, timeouts, mixed-fallback enable and limits, guest firmware on or off, entry roots. BIOS provenance is proposed as not a config key: it is the manifest's own field (section 4, Q21). They are resolved once at packaging time and written into `runtime-host.json` (schema 1, section 4). The packaged host reads them through H1.
2. **Host settings (launch-time).** Values that affect only presentation, input, and host-side output, not guest semantics: window size, presentation mode, input device mapping, memory-card file paths. Diagnostics output paths are not listed here: they are existing packaged CLI inputs (H7). These are consumed by the launcher (Studio, GameWindow, or CLI `run`) before a run starts.

The packaged host reads no configuration setting in this design. Its diagnostic output flags are existing host inputs (H7: `--diagnostics`, `--loaded-code-diagnostics`, `--frame-out`), not configuration, and this design does not change them. Its read list is H1 to H15 in 2.2 as read today, plus H16, a required read that does not exist yet (to be added by Issue B). No config file and no new environment variable is added to that list. The one new packaged file is the integrity carrier `runtime/build-manifest.json`, which the host reads for the H2 and H3 check (3.4). It is a proposed new packaged input, pending Q13. So:

- The ADR-027 Step C baseline is the full layout in 2.9: `<game>[.exe]`, `runtime/PSXRecomp.RuntimeHost[.exe]`, `runtime/runtime-host.json` (every package), `runtime/artifact-image.bin` (HLE packages only), and `README.txt`. Under the relayed Option A, pending owner confirmation in a recorded form, the two binaries are outside the config contract (Q16, Option A; owner ruling relayed to the coordinator on 2026-10-29, not recorded in the repository or in any issue comment read for this doc; see Q16), and their identity belongs to #46 (W14). Integrity still applies (section 3.4): H2 is checked against `binary.sha256` and H3 against `packaged.imageSidecar.sha256`, both in `runtime/build-manifest.json`. The carrier `runtime/build-manifest.json` is the one packaged input this design adds, and it is H16, a required read that does not exist yet (see above and Q13). The firmware inputs (H4, H5, H9, H10) and H6 to H8 and H11 to H14 are outside that baseline; they already ship and this design does not add them.
- A host setting that must reach the packaged run needs one of two changes, and each changes the Step C baseline: a new execution field in `runtime-host.json` (schema 2, section 4), or a new packaged input or host CLI flag. Such a change is listed as open question Q13 and is not proposed here.
- Memory-card paths are not read by the packaged host today (no field among H1 to H15). They are consumed only where a `RecompiledHostExecutionEngine` is constructed (Q8).

This split keeps the Runtime execution contract unchanged: the guest sees only the frozen values in the manifest.

### 3.3 Field rules

- Every key has one owner module and one default defined in code, not in the file (single table of defaults; see 6.3).
- Unknown keys fail the load (fail closed). No silent drop.
- Numeric keys have explicit bounds where the reader checks them (9.1). Timeouts are finite (the 4 h GUI cap at `src/PSXRecomp.Cli/PackageCommand.cs:52` is the precedent). The packaged segment budget is not bounded by a check (9.1).
- Paths are stored as given and resolved relative to the file that holds them, never to the working directory (PREDICTED; this avoids the ambiguity between CLI and GUI launches). Only the per-user store holds paths (section 5.1).

  - H3: the host reads the image once into `imageBytes` (`src/PSXRecomp.RuntimeHost/Program.cs:248`), computes the SHA-256 of that same array, and only then builds `imageWords` from it. `src/PSXRecomp.Infrastructure/Standalone/PackagedArtifactLiveRunner.cs:46` has the same shape and must be changed the same way. No second read of the file is allowed between the hash and the use.
  - H2: the artifact is launched by the operating system from a path (`prebuiltArtifactPath`, `src/PSXRecomp.RuntimeHost/Program.cs:229`), and process creation takes a path, not a handle. A handle on the original file therefore cannot be the object that runs. Checking the path alone leaves the file replaceable between the hash and the launch. The method is proposed here as a private copy, and the owner confirms it as Q18:
    1. The host creates a private directory for the run, with an unpredictable name and an access control list that gives write and delete rights only to the running user. The target platform here is Windows. The directory is outside the distribution.
    2. The host reads the original artifact once into a buffer, and writes that buffer to the private copy, created with create-new so that an existing file is an error.
    3. The host opens the copy for reading with sharing `FileShare.Read` only (no write or delete sharing) and holds that handle until the release point decided under Q18. W12 proposes that point: the return of the `RunSegment` call that launches the copy (Q18, option (ii)). The owner may choose release after process creation instead (Q18, option (i)). Under option (ii) the host does not need to detect process creation. Process creation (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:1352`, inside `RunProcess` at `src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:1310`) happens inside that `RunSegment` call (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:857` is the call site). `ForPrebuiltArtifact` (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:628`) only constructs the engine and does not launch it. The SHA-256 is computed over the bytes read through that handle, and the value must equal `binary.sha256`. This is W12's proposal, not a decided design. W14 at `992c407` (`docs/design/issue-46-artifact-provenance.md`, section 3.9 Issue B (f), and section 9 item 18) leaves the release point as an open owner decision and does not adopt option (i) or option (ii). Q18 is the owner question.
    4. The engine starts the copy: `Process.Start` (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:1352`) runs inside the engine, from the path the host passes to `ForPrebuiltArtifact`. The start happens while the handle is held (step 3). Under the Windows sharing rule, a file opened with `FileShare.Read` denies write and delete sharing to other opens while that handle is open, so the started bytes are the hashed bytes. This sharing behaviour is UNVERIFIED in this document: no test checks it. The implementation must add a test in which a different principal (a different Windows account, or a token whose ACL membership differs; a second process of the same user does not count) attempts a write and a delete of the copy while the handle is held. The claim stands only if that test passes.
    5. The host never launches the original path. Deletion of the private directory is conditional, and it is never unconditional (Q18, deletion options D-a and D-b):
       - Under deletion option D-a, the host deletes the directory only after the exit-confirmation result reports that the child exited and that no residual process remains. Any other outcome leaves the directory in place.
       - Under deletion option D-b, the host does not delete the directory during the run. It leaves the directory in place and reports it as a residual, with its path, in the run result. A later cleanup step removes it.
       A failed deletion is reported as a residual. It is not ignored.
    Steps 3 and 4 rely on Windows sharing semantics. The POSIX equivalent is UNVERIFIED and is decided in the implementation issue (3.5). The firmware packaged run is another packaged launch path: `src/PSXRecomp.RuntimeHost/Program.cs:240` calls `FirmwareRuntimeLauncher.Run` (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:639`), which calls `ForPrebuiltArtifact(artifactPath, ...)` at `src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:691` with the `RuntimeHost` launch mode (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:700`). The H2 check, to be inserted at `src/PSXRecomp.RuntimeHost/Program.cs:229` (not present at 2e3ecad), runs before that branch, so the private copy path must replace `prebuiltArtifactPath` for the firmware branch too. The `RuntimeHost` mode reaches the same unconditional `RunProcess(_binaryPath, ...)` call at `src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:857`, and the mode changes only the arguments (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:799-805`) (CONFIRMED by control flow). The procedure applies to it. The host therefore creates the handle there and keeps it alive across the call to `FirmwareRuntimeLauncher.Run` at `src/PSXRecomp.RuntimeHost/Program.cs:240`. `Run` (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:639`) builds its own engine in the `using` block at `src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:691`, and the handle is released at the Q18 release point. ## 5. Relation to project configuration, and privacy

### 5.1 Privacy of path-valued keys

Path values are not safe in a shareable file. A path such as `C:\Users\<name>\...` reveals a local account name and directory layout. A Project directory is likely to be copied, zipped, committed, or attached to a bug report, so path values must not sit there. This design therefore splits storage by content:

- **Project directory** (treated as shareable; an assumption, Q6): `project.json` (identity and format only, 2.5) and `runtime-config.json`, holding only non-path keys (`execution` and the non-path `host` keys) and per-title overlays (section 7) that contain no path keys.
- **Per-user store** (not shareable): a file in the user's own application data folder, keyed by `ProjectId`, holding path-valued keys only (`memoryCard.slot1Path`, `memoryCard.slot2Path`). Its exact location is UNVERIFIED: no existing per-user settings convention was confirmed in the repository (Q14).
- **CLI or environment only, never stored**: diagnostic output paths `--diagnostics`, `--loaded-code-diagnostics`, `--frame-out` (H7), and the environment variables that name output paths, `PSX_UNIT_TRACE_FILE` (H12), `PSX_GUARD_STATS_FILE` (H14), `PSXRECOMP_IPC_PROFILE` (H11) and `PSXRECOMP_TRANSITION_ATTRIBUTION` (H13). Each is named per invocation or per shell session and is never written to any file in this design.
- **Environment only**: the BIOS location (H6, `PSXRECOMP_BIOS_ROM`). It is never copied into any file.
- **Bindings check before placement.** `input.ports[].bindings` (section 3.2) may hold device identifiers that reveal host hardware or a machine. Its schema is deferred to #47, so the `input` section is not written to any file until the binding schema has been checked for host-specific data (device identifiers, paths, machine or user names).

Consequences:

- A Project directory copy never leaks a host path. A title overlay cannot carry a memory-card path, so the rule "a per-title override never changes host paths" is structural, not a convention.
- The packaged distribution never contains any of these keys, because the packaged host reads none of them (3.1).
- Q6 asks whether the Project directory is in fact the shareable unit. If it is not, the non-path keys can also move to the per-user store, but the rule that paths never enter the Project directory stays.

- `project.json` is the Project management manifest (`src/PSXRecomp.Core/Project/ProjectManifestDocument.cs:6`). It records identity (`ProjectId`, `InputSha256`) and format (`SchemaVersion`, `ArtifactKind`). It is not a settings store, and it should stay that way (PREDICTED).
- Runtime configuration is a separate file, in the Project directory, named `runtime-config.json` (proposed; name UNVERIFIED against any existing convention).
- `project.json` gains no runtime fields. Its single-purpose meaning is preserved, and a runtime-config change never needs a Project format bump (PREDICTED).

## 6. Shared GUI and CLI method

### 6.1 One model, two front ends

- The domain port is `IRuntimeConfigStore`, declared in `PSXRecomp.Core` (new, Domain). It follows the `IProjectMetadataStore` pattern (`src/PSXRecomp.Core/Project/IProjectMetadataStore.cs:18`, CONFIRMED). The `RuntimeConfig` record and its validation live in `PSXRecomp.Core` with no I/O.
- The concrete store, the file reads and writes, and the per-user store location live in `PSXRecomp.Infrastructure`, following `FileProjectMetadataStore` (CONFIRMED pattern).
- Environment-variable reads happen only in Infrastructure. This follows `docs/architecture-matrix.md` Layer rule 2 (Infrastructure executes host APIs) and rule 3 (Application does not acquire host resources directly), and `src/architecture.contract.json:22` (Domain forbids `System.Environment`). The Studio and GameWindow read no environment variable directly; they call the Infrastructure store. OBSERVED: the existing read at `src/PSXRecomp.RuntimeHost/Program.cs:239` sits in an entry point outside any Infrastructure adapter. Its layer classification is UNVERIFIED and is not changed by this design.
- The CLI maps its existing parsed options onto a partial `RuntimeConfig` overlay (`ParsedArguments`, documented near `src/PSXRecomp.Cli/Program.cs:508`, CONFIRMED). The CLI does not gain a new parser.
- The Studio binds its settings UI (not present today, 2.3) to the same `IRuntimeConfigStore`. It must not keep a separate copy of any default.
- Budgets currently duplicated in `RunCommand`, `RealRomTitleExecutionService`, `MixedFallbackOptions`, and `FirmwareDistributionRequest` (2.7) are replaced by references to the single defaults table (6.3). This is a refactor, and it changes no value unless the owner decides a value is wrong.

### 6.2 Precedence (lowest to highest)

Execution layers (1, 3, 4, and 6 for `package`) are resolved at packaging time. Layer 6 for `run` is resolved at run time, and `run` does not produce a packaged artifact. Host layers (2, 3, 4, 6) are resolved at launch. Each layer is tagged with which kind it affects.

1. Compiled-in defaults (the single defaults table, 6.3). Execution and host.
2. Per-user store (path-valued keys only, 5.1). Host only, launcher-side.
3. Project `runtime-config.json`. Execution at packaging; host at launch.
4. Per-title overlay for the matching title identity (section 7). Execution at packaging; non-path host at launch.
5. Not a precedence layer: environment variables. They never take part in the precedence order above, so no configuration value overrides them or is overridden by them. Launcher-side and generated-code-side. They do not set execution settings through this table. The environment reads that change run behaviour are listed in 9.2.
6. CLI options for one invocation. Execution at packaging (`package`) or at run (`run`); host for the diagnostic flags.

The BIOS location (H6) is an input path, not a layer. It is not overridden by any layer.

A value that a higher layer does not set is inherited, not reset. Each effective value must record its source in the output (the `--json` result or the packaged `README`), so a result can be traced to a layer.

### 6.3 Single defaults table

One module in `PSXRecomp.Core` holds every default in 2.7, with a name and a comment for each. Existing constants are re-pointed to it. Each value keeps its current number until the owner changes it; the duplicated and inconsistent values (1_000_000 versus 4096, and 100_000_000 for firmware) are listed as open question Q1, not silently unified.

## 7. Per-title overrides

- **Key.** A title is identified by `DiscIdentity` (serial, region, revision, `DiscIndex`; `src/PSXRecomp.Core/TitleIdentity/DiscIdentity.cs:10-14`, CONFIRMED). The override key is serial, region, revision, and discIndex, as in the identity of section 3.2 (`identity: { serial, region, revision, discIndex }`). So each disc of a multi-disc title has its own overlay (PREDICTED; UNVERIFIED how the Project records disc order). Two points about the key are open, and Q2 asks both: whether discIndex belongs in it, and how the Project records disc order (UNVERIFIED).
- **Location.** Per-title overlays are stored in the Project directory, under a sub-folder keyed by the title identity, not in the application-wide settings. The Project directory is treated as shareable (Q6), so overlays hold no path-valued keys (5.1).
- **Allowed keys.** Execution keys may be overridden per title (for example a larger budget for a slow title). Non-path host keys may be overridden per title (for example controller mapping). Path-valued keys and diagnostic outputs may not be overridden per title, because they are not stored in that file. Debug keys may not be made permanent per title in a production profile (see 9).
- **Applied at packaging time** for execution keys. The effective value is frozen into the manifest. A per-title override therefore never needs a runtime lookup.
- **Not a source of identity.** An overlay never changes `ProjectId` or `InputSha256`, and it never changes which input file is accepted.
- **Mismatch.** If the overlay's identity does not match the loaded image's identity, the overlay is refused with a classified error, not ignored (PREDICTED; mirrors the fail-closed rule for manifests).

## 8. Configuration versioning and migration

### 8.1 Current behaviour (CONFIRMED)

- Each persisted file has its own integer version and a strict-equality check. Readers reject any other version, and there is no migration (2.5).
- The rule that a shape or meaning change requires a bump is stated in the doc comment of `ProjectFormatVersion` (`src/PSXRecomp.Core/Project/ProjectSchema.cs:15-17`, CONFIRMED). `ProjectMetadataSerializer` enforces the version by strict equality (`src/PSXRecomp.Core/Project/ProjectMetadataSerializer.cs:81-85`, CONFIRMED). That rule is good and should be kept.

### 8.2 Proposed policy for `runtime-config.json` and the per-user store

- Each file carries a top-level `schemaVersion` (integer) and `kind` (`"psxrecomp.runtime.config"`, or the per-user store's own kind), like `project.json`.
- Strict reject of versions newer than the reader understands. The message names both versions, as `RuntimeHostManifestJson` already does (CONFIRMED pattern).
- Older versions are migrated in memory by a pure function `Migrate(vN) -> vN+1`, one step at a time. The migrated document is written back only on an explicit save, never silently on load (PREDICTED; keeps the user's file unchanged until they choose to change it).
- Each migration step ships with a test that loads a frozen fixture of the old version. Fixtures contain no real titles, no BIOS data, and no paths from a real install.
- Unknown keys fail the load (3.3). This makes a typo visible instead of silently ignored, and it is also how an old reader refuses a newer file.
- The packaged `runtime-host.json` keeps its own schema version (1, 2.5). A change to runtime-config never implies a change to the manifest unless the execution section changes (section 4).

### 8.3 Version 1 of runtime-config

Version 1 is the first version; there is nothing to migrate from. The first implementation should adopt the keys that already exist as CLI options (2.1) and nothing else, with one exclusion: `--segment-budget` is not in v1. It has no packaged carrier (section 4, Q15), and for `run` it stays a CLI option outside runtime-config. `package` rejects it today (`src/PSXRecomp.Cli/Program.cs:57`). BIOS provenance is also not a v1 key: it is proposed as manifest-only (section 4, Q21). v1 does not change any packaged segment budget. Their current values are recorded in section 4: the headless embedded budget is `DefaultSegmentBudget`, and the `--gui` embedded budget is `uint.MaxValue`. Whether the embedded budget reaches the host's run is UNVERIFIED (section 4). Host keys are added in a later version, each with a migration step that adds defaults for the missing keys.

## 10. Recommendation

1. Adopt the two-tier model (3.1): frozen execution settings in the packaged manifest, and launch-time host settings applied by the launcher. The packaged host reads one new input for integrity, the carrier `runtime/build-manifest.json` (3.4). It is a proposed new packaged input, pending Q13, and it reads no new configuration input. The carrier changes the ADR-027 Step C layout (2.9), which does not list it, and Q13 stays open. Its two program binaries, `<game>[.exe]` and `runtime/PSXRecomp.RuntimeHost[.exe]`, stay in the baseline. The recommendation that they are outside the config contract is conditional on Q16 being recorded: under Q16's Option A (relayed, unrecorded in source; the owner must confirm it in a recorded form), they are outside the contract, with their identity in #46. The packaged host checks H2 against `binary.sha256` and H3 against `packaged.imageSidecar.sha256` in `runtime/build-manifest.json`, failing closed, and the game window (H15) does the same (section 3.4). This integrity check is a W12 requirement and is not contingent on the relayed Q16 ruling, which concerns only the contract membership of the binaries; the firmware and environment inputs H4 to H14 are outside that baseline (2.9, Q13).
2. Keep `runtime-host.json` schema 1 as the execution carrier. Do not add fields in this issue. Map the existing CLI options to it (2.1, 2.5). `segmentBudget` has no schema-1 field; v1 changes no packaged segment budget (section 4, Q15), and BIOS provenance is not a v1 key (proposed manifest-only, section 4, Q21), and it is not silently dropped.
3. Add `runtime-config.json` (Project directory, non-path keys only) and a per-user store (path-valued keys only), both behind an `IRuntimeConfigStore` port in Core with the implementation in Infrastructure (5.1, 6.1).
4. Create a single defaults table and re-point the constants (6.3). The table can be written now with each value at its current number (6.3). Q1 asks whether the inconsistent segment-budget defaults should be unified, and that changes a value only when the owner decides.
5. Implement per-title overlays only after the title-identity key is confirmed (Q2), and only with non-path keys (section 7).
6. Keep audio, VSync, and graphics backend as reserved names in the design until their host adapters exist (2.8, 3.2). Do not invent keys for them.
7. Split debug and production profiles (9.2). Keep debug keys out of execution settings, and refuse the guard build flag in production, which removes the guard-build reads from packaged artifacts. The host-side reads remain (9.2).

Suggested order of follow-up work (for the owner to schedule; not started here): defaults table, then runtime-config version 1 with only the existing CLI keys, then per-title overlay, then host keys one area at a time with #40 and #47.
