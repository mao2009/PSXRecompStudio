### 3.1 Identity classes

Keep four identities separate. Collapsing them is what caused the problems in #734, which this design follows (`docs/runtime/loaded-code-identity.md`).

1. **Input identity.** SHA-256 of the input bytes that the codegen consumed: the EXE file for PS-X EXE input (`src/PSXRecomp.Cli/CliInput.cs:84-85`), or the CHD stream for CHD input (`src/PSXRecomp.Cli/CliInput.cs:106-109`). It identifies provenance. It is not a runtime proof. Source: `CliInput.LoadWithIdentity`.
2. **Build key.** A hash of everything that decides the generated source and the build recipe, computed before building. Its inputs are listed in 3.2. The key records what was built. It is not a skip key, because Skip is disabled in v1.
3. **Source identity.** SHA-256 of the generated `.c` bytes. Computed after codegen. It is specified to be recorded and verified (Issue A), and it identifies what was generated.
4. **Binary identity.** SHA-256 of the native binary. Computed after the build. It is the artifact identity that `src/PSXRecomp.Cli/RunCommand.cs:191` already reports, but only after a run.

Binary identity is not guaranteed to be stable across builds (Section 4.3). The design specifies that the source and binary hashes are recorded and verified. It makes no stability promise for either.

### 3.2 Build key inputs

The build key hashes this set. Each item is a field in the manifest, so a mismatch is explainable:

- Input identity (item 1 of 3.1). The input SHA-256 is computed in the CLI by `CliInput.LoadWithIdentity` (`src/PSXRecomp.Cli/CliInput.cs:56`). `recompile` does not call it today (`src/PSXRecomp.Cli/RecompileCommand.cs:39` calls `Load`), so `recompile` must switch to it. `package` and `run` already call it (2.1). The value reaches the workflow as `ArtifactBuildRequest.InputSha256` (Section 7.2). For a standard artifact, the runtime-input names are in 3.5 (`runtimeInputs`).
- Input kind: `exe` or `chd`, chosen by file extension (`src/PSXRecomp.Cli/CliInput.cs:44-46`). It is keyed, because it selects the loading path that produces the IR.
- Requested binary name (`BinaryName`). In standalone mode it is derived from the input file name (`src/PSXRecomp.Cli/RecompileCommand.cs:63`, `ResolveStandaloneArtifactName` at `:213`). It is a bare file name, not a path. On Windows `PackageCommand` passes the directory name plus `.exe` (`src/PSXRecomp.Cli/PackageCommand.cs:124`), and the carrier records that requested name (3.5, binary file name rule). Two inputs with identical bytes and different names therefore have different keys, and their manifests differ in `source.file`, `binary.file`, and `object.file`.
- Entry roots: `arguments.EntryRoots` (`src/PSXRecomp.Cli/RecompileCommand.cs:40`), passed into `CliInput.Lower` (`src/PSXRecomp.Cli/CliInput.cs:130-136`). They change the lowered program and therefore the generated source. The key holds them as a list of decimal values, in order. An empty list means no explicit roots.
- Segment budget (`src/PSXRecomp.Cli/RecompileCommand.cs:38`), keyed as `Codegen.Budget`.
- SHA-256 of the generated `Source` text (`source.sha256`). The CLI runs codegen before the workflow is called (`src/PSXRecomp.Cli/RecompileCommand.cs:42`, `:86-101`), and the workflow holds the result. This hash covers every input that changes `Source` that is not listed above, including the loaded-code table.
- Extra compiler or linker arguments. They are recorded in the manifest as given (`extraArguments`), and their presence is part of the record. They are rejected only if a token contains `/`, `\`, or `:`, which is the single rule of 3.6.
- Codegen mode and standalone options, as the `codegen` fields listed in 3.5. Mode is standard or standalone (`src/PSXRecomp.Cli/RecompileCommand.cs:56`).
- Codegen options: `traceUnits`, `guardStats`, `allowEmptyProgram` (2.4). These must be part of the key. Today they are not recorded anywhere.
- Loaded-code table (`src/PSXRecomp.Core/Recompiler/LoadedCodeTable.cs`) identity, from `LoadImageManifest`. Its source SHA-256 is already computed (`src/PSXRecomp.Core/Recompiler/LoadImageManifest.cs:356`). Loaded-code names are not keyed separately. The CLI `recompile` path passes no loaded-code table: `src/PSXRecomp.Cli/RecompileCommand.cs:42` calls the single-argument `Generate`. On the engine path, the table is covered by `source.sha256`. Its descriptors go into the manifest as an explanation only.
- Generator version (3.3).
- Build recipe, path-free (3.6): the fixed compiler and linker tokens, the caller's extra arguments, `FirmwareDistribution`, and the `--gui` linker arguments. No absolute path and no staging GUID enters the key.
- Toolchain identity. Every component below is a version line or a triple, never an executable path. The workflow must resolve the driver once, as `compiler = request.CompilerExecutable ?? GccGeneratedHostRecipe.DefaultCompiler` (`"gcc"`; the adapter default is `src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:24`, the override field `src/PSXRecomp.Core/Recompiler/GeneratedHostBuild.cs:52`). It must pass `compiler` to `IToolchainProbe.Probe` and must set `CompilerExecutable: compiler` on the build request. Both must receive the identical string.
  - Driver version: the first line of `<compiler> --version`.
  - Target triple: from `<compiler> -dumpmachine`.
  - Linker version: the link step runs the same driver (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:105`), which invokes `ld`. The probe runs `<compiler> -print-prog-name=ld` to locate the linker, then keys the first line of that linker's `--version`. The linker path is not keyed. If the driver prints a bare `ld` with no directory, the probe runs `ld --version` through `PATH`, which is the same resolution the build uses. The classification rule is in 7.2 (probe contract): a linker or driver that is not found gives `Available` false; a version run that starts and fails gives `PackagingStepFailed` with `FailedStep` `probe`, not `Available` false.
  - C library (accepted limit). The C runtime and import libraries are not probed or keyed. A change is not detected. Because the build always runs, the next build uses the changed library, but its manifest does not record the change. ### 3.5 Manifest contents and location

**Binary file name rule (Windows and other platforms).** `PackageCommand` takes the output directory name (`src/PSXRecomp.Cli/PackageCommand.cs:122`) and sets `binaryName` to that name plus `.exe` on Windows, and to the bare name elsewhere (`src/PSXRecomp.Cli/PackageCommand.cs:124`). The adapter writes `<binaryName>.c` and links `<binaryName>` (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:55` and `:101`). If the toolchain produced `<binaryName>` as requested, that is `binary.file`. If that file is absent, the adapter's resolution looks for `<binaryName>.exe` (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:316-321`), and that name is `binary.file`. `binary.file` depends on the toolchain's output, not on the caller alone. `ResolveBinaryPath` returns the requested path when that file exists (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:318`) and otherwise looks for `<binaryName>.exe` (`:316-321`). On the usual MinGW output, a Windows HLE build therefore records `binaryName` as `x.exe`, `binary.file` as `x.exe`, and `source.file` as `x.exe.c`. A `RecompileCommand` name, which the caller does not suffix, is recorded bare, and `binary.file` is `<binaryName>.exe` only if the toolchain produced that name. The resolution does not produce `x.exe.exe` for a requested `x.exe`, because the requested file then exists.

**Nullable keys of schema v1.** Exactly these keys may be `null`, and no others: `buildKey`; `codegen.initialGprSha256`; `codegen.initialMemorySha256`; `codegen.programImageInputSha256`; `codegen.generatorVersion`; `loadedCode`; `toolchain.compilerVersionLine`, `toolchain.linkerVersionLine`, `toolchain.targetTriple`, and `toolchain.recipeTokens`; and `productRevision` (when the attribute is absent). The list is the same in 3.9 (e) and (g), in 3.10, and in the schema comments above. Every other key is required in each carrier kind in which it applies, as the next paragraph states. Owner ruling (2026-10-30, W12 Q19): option (a). `null` is allowed for exactly these keys and no others. The reader rules are in 3.10. W12 at `a6027a2` records Q19 as ruled (section 11, line 514).

**Required and optional keys per carrier kind.** An HLE carrier (`PackageCommand`) has every key present: `packaged` and `object` are present, and `runtimeInputs` is an empty list, because `externalBios` is false there. A firmware carrier (`FirmwareDistribution`) has every key present except `packaged` and `object`, which are absent. A `runtimeInputs` entry of kind `environment` has `name`, `kind`, and `requiredBy` only, with no `sha256`. ### 3.6 Path-free recipe

The build key and the manifest must not depend on where the build runs. Today the compiler and linker argv carry output-dependent values, all built from `OutputDirectory`: `sourcePath` (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:55`, passed at `:83`), `objectPath` (`:76`, passed at `:85`), and `binaryPath` (`:101`, passed as `-o` at `:219-220`). The current firmware path stages into `.<artifact>.staging-<guid>` (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:510`), so the values built from that staging directory also carry a random GUID on every build. The raw argv is therefore run-dependent, and the design does not record it.

The recorded `recipeTokens` are these fixed tokens, in order:

- `DefaultCompilerArgTokens`: `-std=c11`, `-O0`, `-Wall`, `-Wextra`. Today this is a private array in the adapter (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:25`), so the Domain workflow cannot read it. See "Recipe ownership" below.
- The caller's `ExtraCompilerArguments`, as given.
- `-c`, then the placeholder `<source>`, then `-o`, then the placeholder `<object>` (`:82-85`).
- For the link step: `<object>`, then `-s` when `FirmwareDistribution` is set (`:102-103`), then the caller's `ExtraLinkerArguments`, then `-o`, then the placeholder `<binary>` (`:219-220`).

The placeholders `<source>`, `<object>`, and `<binary>` replace the three output-dependent values. Real paths go only into the local history record (Section 5).

**Caller-supplied extra arguments: rule.** The workflow must reject, before any build step, an extra compiler or linker argument that contains `/`, `\`, or `:` anywhere in the token. This covers rooted paths, drive-qualified paths, and forms such as `-I/does not exist/include`. `Path.IsPathRooted` is not enough, because it returns false for `-I/...`, and the adapter test at `src/PSXRecomp.Tests/Infrastructure/GeneratedHostBuildServiceTests.cs:213` uses exactly that form. A rejected request must return an outcome `ArgumentRejected` with code `PATH_ARGUMENT_NOT_ALLOWED` (a proposed name, not present at this SHA), must make no port call, and must create no staging area. The rule is to sit in the workflow. The adapter keeps accepting such tokens, so its existing test stays valid. The rule would also reject a few non-path tokens that contain `:`, such as `-Wl,--subsystem,windows:5.0` and `-DURL=http://...`. No production caller passes them, so that cost is accepted.

Tokens without a separator, such as `-Iinclude`, are accepted and recorded as given. They resolve against the process working directory, which is not keyed. That is an accepted limit (3.7).

**Recipe ownership.** The fixed tokens move into a Domain constant, `GccGeneratedHostRecipe` (`[Domain]`, `src/PSXRecomp.Core/Recompiler/GeneratedHostBuild.cs`). It holds `DefaultCompiler` (`"gcc"`), `DefaultCompilerArgTokens`, the literals `-c`, `-o`, and `-s`, and the three placeholders. The adapter must consume this constant (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:25`, `:82-85`, `:102-103`) and must not keep its own copy. The workflow must compute `recipeTokens` from the same constant. The constant is named for gcc because every flag in it is a gcc flag. A second toolchain needs its own kind (for example an enum with `Gcc` and `Mingw`, keyed in the build key) and its own recipe constant. No such kind exists today. A change to a flag must therefore change the key, and the adapter must not drift from it. This move is a required change and is not implemented by this design.

The tier-1 test in Section 4.2 is specified to check this rule: the same input built into two different directories gives the same `buildKey` and the same manifest bytes.

### 3.7 Environment, PATH, working directory, and driver inputs

Each input that could change the output is one of three classes:

- **Keyed**: it is in the build key or in a checked identity in the manifest.
- **Presence-reported**: the probe reports whether it is set. The name goes into the local history entry. The build still runs. The name is not keyed, because the key must not depend on the machine.
- **Out of scope for the key**: it does not change output bytes under the stated basis, or it is not read by the build. The reason is given.

Since Skip is disabled, no class triggers a Skip decision. Every build runs.

**Presence-reported list.** `RunToolchain` does not set or clear the environment (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:244-250`), so the child process inherits the parent's variables. The probe reports the names that are set, using ordinal, ignore-case comparison. Windows environment names are case-insensitive, so `cpath` and `CPATH` are the same name. The fixed list is `CPATH`, `C_INCLUDE_PATH`, `CPLUS_INCLUDE_PATH`, `OBJC_INCLUDE_PATH`, `LIBRARY_PATH`, `COMPILER_PATH`, `GCC_EXEC_PREFIX`, `LD_RUN_PATH`, and `GNUTARGET`. Any name beginning with `GCC_` (prefix rule) is also reported, which includes `GCC_COLORS`. The list is owned by the probe, `ProcessToolchainProbe` (Infrastructure; 7.2). The workflow receives the names and does not own the list. It cannot cover every variable a toolchain might read. No environment hash is kept. An earlier draft kept one to gate Skip. That draft is withdrawn with Skip.

**Accepted limits.** A tracked limit is accepted only while it is stated. The owner rule is: when a limit could have changed, rebuild. In v1 the build always runs, so every build takes the changed input into account. The limit that remains is about the record. The manifest of a build does not show an untracked change (for example a C runtime update or a driver configuration edit), so the manifest cannot prove that such a change did not affect the output. Operators must treat these triggers as review events:

- any update of the C runtime or import-library package, including a runtime-only update that leaves the driver version line unchanged;
- any edit to a driver configuration file (`<driver>.cfg`) or to a `@file` response file;
- any reinstallation or edit of the toolchain directory, or a change of what `PATH` and the working directory resolve to.

The workaround is the same for each: rebuild. Because the build always runs, a rebuild runs the build again. ### 3.8 Digests read by the packaged host (H2, H3)

Issue B requires the packaged host (issue #48, W12) to verify its inputs before use: H2 for every package, and H3 for HLE packages only. No check exists at this SHA. `src/PSXRecomp.RuntimeHost/Program.cs:229` only resolves the H2 path, `:244-248` only resolves and reads the H3 image, and no SHA-256 or verify code exists in `src/PSXRecomp.RuntimeHost`. Issue B adds the checks. The fail-closed rules are those of W12 section 3.4, summarised in the paragraph "Fail closed" below. H2 is the game artifact named by `manifest.Artifact` in `runtime-host.json` (W12 section 3.4). H3 is the program image sidecar named by `manifest.Image` (`artifact-image.bin`). The expected digests live in one carrier, `build-manifest.json`, described in 3.5. They are not in `runtime-host.json`, because that would be a schema-2 change, which W12 Q16 (Option A, relayed; owner to confirm in recorded form) does not take (W12).

**Carrier fields, one per digest.**
- digest H2: `binary.sha256`, with `binary.file` as the bare file name of the artifact.
- digest H3: `packaged.imageSidecar.sha256`, with `packaged.imageSidecar.file` (`artifact-image.bin`, `RuntimeHostLayout.ImageFileName`, `src/PSXRecomp.Infrastructure/Standalone/RuntimeHostLayout.cs:45`). **H3 applies to HLE packages only.** A firmware package has no sidecar and no `packaged` block, and H3 is not checked for it. The sidecar is written only on the HLE path (`src/PSXRecomp.Cli/PackageCommand.cs:231`), and firmware packages are routed away before that (`src/PSXRecomp.Cli/PackageCommand.cs:70-72`).

**H3 is not `codegen.programImageInputSha256`.** The codegen field is the hash of the bytes passed to codegen. It is computed before the build and is a key input (`src/PSXRecomp.Cli/PackageCommand.cs:155`). H3 is the hash of the file the packager writes after the build (`src/PSXRecomp.Cli/PackageCommand.cs:231`). The two values are the same only if both see the same bytes. The basis is that both call the same function, `ProgramImageBytes(input.InstructionWords)`, and that function writes each word little-endian with no header (`src/PSXRecomp.Cli/PackageCommand.cs:322-330`). No code in `src/` computes either hash today (grep, OBSERVED). **Equality is UNVERIFIED** until a test hashes the written `artifact-image.bin` and compares the result with the codegen input bytes.

**Location (requirement).** A packaged build, HLE or firmware, must write the manifest to `runtime/build-manifest.json` and must write nothing at `<outputDir>/build-manifest.json`. For an HLE package the manifest must sit beside the sidecar. A non-packaged build must write `<outputDir>/build-manifest.json`. A build must have one location and one writer.

**Firmware packages (carrier).** A firmware package (`FirmwarePackageCommand`, routed at `src/PSXRecomp.Cli/PackageCommand.cs:70-72`) must have its carrier at `runtime/build-manifest.json`, with `binary.sha256` (H2) and no `packaged` block. H2 applies to every package. At this SHA the host does NOT check H2: `src/PSXRecomp.RuntimeHost/Program.cs:229` is the artifact path resolution (`RuntimeHostLayout.ResolveArtifactPath`), and no SHA-256 check exists in `src/PSXRecomp.RuntimeHost`. Issue B adds that check, before the firmware branch (W12 section 3.4; W12 describes the check as required, not as present). Without this carrier, a firmware run under Issue B would have no expected digest and would have to fail closed every time. The writer must be the firmware packaging caller (`FirmwareDistribution`), which builds the artifact into its staging directory (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:426-427`). It must write the carrier as the last file written into the staging area, after `runtime-host.json` (`:482`) and the README (`:484`), and before the commit (`:487`). Moving that caller onto the writer is part 2 of the migration in 7.2, and it is part of Issue A (3.9).

**Writer and order.** `ArtifactBuildManifestWriter` (pure, Domain) produces the carrier text. The packaging code path writes that text through `IBuildArtifactStore.WriteText` into the staging area. The order must be the same for every packaged build, HLE and firmware (a proposed order; the steps are those of 7.2, and every packaged file is written into staging before one commit):
0. **Pre-check (the required first step, for every packaged kind, HLE and firmware; Q8 option (i)).** If the output directory exists and is not empty, refuse with the classified error `OUTPUT_DIRECTORY_NOT_EMPTY` (proposed code). Write nothing, delete nothing, and create no staging area. Otherwise continue. The check is `IBuildArtifactStore.IsEmptyOrAbsent(outputDirectory)` (proposed, owner Issue A). It runs before `CreateStaging`, the build, and the commit, and it is repeated inside the commit under the commit rule below, because a concurrent run can create the target after this check. It also precedes staging-directory creation: at `2e3ecad` the firmware path calls `StagingDirectoryFor` at `src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:372`, and that method creates the parent directory at `:509` before any build, so in the firmware path the check comes before `:372`. **Commit rule for packaged outputs (Issue A; required).** The commit is a no-replace move of the staging directory to the output path. It never backs up, swaps, or deletes a non-empty output directory; it removes an empty one only through step (2). No packaged path performs a recursive delete on the output directory or on any user path: the output directory is refused, never removed. The only recursive removal the design allows is `Discard` of the staging tree that this tool created (Section 7.2), which is containment-checked and never reaches the output directory (requirement; not implemented, not run, P-18). The commit runs only under this condition, which is checked first: (a) the staging directory is the one this run created, identified by its run token (`Discard`, 7.2), and (b) neither the output directory nor its parent is a reparse point (a junction, symbolic link, or mount point). If (a) or (b) fails, the commit refuses with a classified error and writes nothing, because a rename under a reparse point can cross volumes (requirement; not run, P-11). Then the steps run in order. (1) `IBuildArtifactStore.IsEmptyOrAbsent(outputDirectory)` is checked. If the target is non-empty, the commit refuses with `OUTPUT_DIRECTORY_NOT_EMPTY`, writes nothing, and deletes nothing. (2) If the target exists and is empty, `IBuildArtifactStore.RemoveEmptyDirectory(outputDirectory)` (proposed, owner Issue A) removes it. That method deletes a directory only if it has no entries at that moment, and it fails without deleting anything if it has entries; the commit refuses if it fails. Immediately before the move, the reparse-point check of (b) is run again, and the commit refuses if the output directory or its parent is a reparse point. If step (2) removed an empty output directory, the output-directory half of this re-check inspects nothing (an absent path is not a reparse point), so only the parent is checked. The safety claim rests on the same-volume requirement and the UNVERIFIED no-replace move of (3). That re-check narrows the window but is not atomic with the move, so the reparse-point safety also rests on the same-volume requirement and the UNVERIFIED no-replace move of (3), which are the gating for this item (Section 9, item 24). (3) `IBuildArtifactStore.Commit` moves the staging directory to the output path by a move that fails when the destination exists. The move in (3) both creates the target and fails when it already exists (UNVERIFIED, as stated in (3)), so it is the final guard, and the guard holds only on one volume. Until that move is verified, the guard is unproven: the safety of the window between (1) and (3) rests entirely on it, and no packaged commit may be enabled before it is verified (Section 9, item 24). The check in (1) is a fast refusal, not the guard, and it is not immediately before the move: step (2) lies between (1) and (3). The guard is the pair (2) and (3). `RemoveEmptyDirectory` removes only a directory with no entries, and the no-replace move refuses an existing destination. ### 3.9 Final rules for the packaged digests (owner ruling, converged with W12)

This subsection records the final rules. Where an earlier paragraph in 3.8 differs, this subsection governs.

1. **Carrier.** `runtime/build-manifest.json` is the digest carrier for every packaged build, HLE and firmware. H2 is `binary.sha256`. H3 is `packaged.imageSidecar.sha256`, for HLE packages only.
2. **Verification is required (Issue B).** The packaged host must verify H2 for every package and H3 for HLE packages. No check exists at this SHA. The check must not be switchable off, and there must be no warning-only mode.
3. **The verified bytes are the used bytes.** The digest must be computed over the same byte sequence the host reads and then uses, not over a second read of the path. For H3 the host must hash the byte array it passes on. For H2 the executable is launched by the operating system from a path, so the hashed bytes and the executed bytes can differ unless the host makes them the same. Open question 18 covers this.
4. **Fail safe.** A missing, unreadable, or unparsable carrier; a missing or unreadable H2 or H3; or a digest mismatch is a setup failure. No guest code may run. This follows W12 section 3.4. The H15 game-window path must run the same checks before its reads.
5. **Single writer, read-only reader.** The single writer is the packaging code path that calls `ArtifactBuildManifestWriter` once per build (3.5, 3.8). The host must only read the carrier and must never write it (Issue B).
6. **No Skip, no key effect.** v1 always builds (Section 6). The digests are outputs and are not in `buildKey` (3.8). **No environment hash is kept in any record.** The earlier draft that kept one is withdrawn with Skip (3.7). Only environment variable names are kept, in the local history (Section 5).

**Tamper resistance is not claimed.** `build-manifest.json` is not signed. A person who can write to the package can change the carrier and the file it describes together. The verification in this section therefore shows that the files match the carrier. It does not show that the carrier is authentic. Tamper resistance, meaning signing, a trusted root, or a protected location, is a separate issue and not part of this design. No document or code comment may describe the carrier as tamper-proof.

## 4. Reproducibility: scope and limits (no guarantee)

**Complete reproducibility is not guaranteed.** This section gives what the key covers and what it does not. It does not promise that a build is reproducible.

### 4.1 What is expected today (tier 0)

Expected, not run: the same IR, with default options, gives byte-identical C source when `RecompilerHostCodeGen.Generate(program)` is called twice in-process. The test `Determinism_Same_IR_Produces_ByteIdentical_Source` (`src/PSXRecomp.Tests/Recompiler/HostCodeGenTests.cs:576`, OBSERVED test name) does exactly that. Its scope is narrow. It calls only the single-argument overload with default options. It does not cover `traceUnits`, `guardStats`, a non-empty loaded-code table, or the artifact driver. The artifact-driver determinism tests (`src/PSXRecomp.Tests/Recompiler/RecompiledArtifactCodeGenTests.cs:144`, `:223`, `:252`, OBSERVED names) cover `GenerateStandalone` and `Generate`, and their option coverage was not checked. The docs state the rules (`docs/development/recompiler-host-codegen.md:301-310`, OBSERVED): fixed naming, fixed indentation, fixed block order by `EntryPc`, no timestamps, GUIDs, random names, or paths.

The code supports those rules: block iteration follows the IR list (`src/PSXRecomp.Core/Recompiler/RecompilerHostCodeGen.cs:288`), loaded code is ordered by entry PC (`:293`, `:937`, and `src/PSXRecomp.Core/Recompiler/LoadedCodeTable.cs:63`). CONFIRMED. The local `var valueNames = new Dictionary<int, string>()` at `src/PSXRecomp.Core/Recompiler/RecompilerHostCodeGen.cs:565` is a method local, not a field, and it is used for lookups in the code I read. I did not confirm that no iteration over a `Dictionary` or `HashSet` reaches the output. UNVERIFIED for the whole file.

Tier 0 does not cover: a different `traceUnits` or `guardStats` setting, a different entry point (`recompile` vs `run` vs `package`), or a different code version.

### 4.2 Proposed key scope (tier 1), not a guarantee

**Status.** The scope and the tests below are required, not implemented at this SHA.

Given the same input bytes (input SHA-256), the same psxrecomp generator version, the same codegen options, the same entry roots, and the same loaded-code table, the generated `.c` is byte-identical (CONDITIONAL: expected for the tested cases only, and UNVERIFIED for the whole file, see 4.1), and the `buildKey` is identical. The manifest's `source.sha256` field is specified to record this, so that a reviewer can verify it once the writer exists. This is a description of what the key covers. It is not a stability promise.

Before this scope is relied on, these tests must exist and pass:

- The codegen options are recorded (3.2), so two builds with different `guardStats` are not the same build.
- The generator version constant exists (3.3).
- Test K-A (required): build the same input twice through the same entry point, into two different output directories. The `buildKey`, the `source.sha256` field, and the manifest bytes must all be identical. The test fails if any path, GUID, or timestamp reaches the key or the manifest.
- Test K-B (later): compare across entry points for the default options.
- Test K-C (required): equal-byte inputs built under two binary names (for example `game-a.exe` and `game-b.exe`) produce different `buildKey` values. Each build runs and produces its own name. Building the second name never reuses the first name's output. This test catches a key that omits the name, which Test K-A cannot catch, because Test K-A keeps the name fixed.
- Test K-D (required): the workflow must reject each of `-I/does not exist/include`, `C:\\lib`, and `-Wl,-rpath,/opt/lib` with `PATH_ARGUMENT_NOT_ALLOWED`. It makes zero calls to `IGeneratedHostBuildService` and creates no staging area. It accepts `-Iinclude`. The test uses a fake port that counts calls.
- Test K-E (required; a different test from P-7): two requests with two distinct, absent output paths, differing only in an extra compiler or linker argument, each call the build port. No code path skips the build. Test K-E does not use a shared target. The same-target race is P-7, a separate test with its own ID.
- Test K-F (required): changing only `EntryRoots` or the input kind changes the `buildKey`, because both change `Source`. The `source.sha256` field must also change.
- Test K-G (required): a fake `IToolchainProbe` and a fake `IGeneratedHostBuildService` both receive the identical `compiler` string. The string is `request.CompilerExecutable` when set, and `"gcc"` otherwise. The test also covers `Available = false`, which must fail with `TOOLCHAIN_UNAVAILABLE` before staging and make no build call.
- Test K-H (required): the probe reports presence for `CPATH`, lowercase `cpath`, `LD_RUN_PATH`, `GNUTARGET`, and `GCC_COLORS`. Each name appears in the local history entry. None of them changes the build decision or the key.
- Test K-I (required): a change in the linker version line alone changes the `buildKey`.

### 4.3 Binary identity (tier 2): not guaranteed, not yet measured

Binary byte-identity is the claim a user would want most, and I could not establish it. The factors that can break it:

- The compiler and linker version, and the target. PREDICTED to change the binary. UNVERIFIED.
- Build paths embedded in the binary. The firmware path strips them with `-s` (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:102`), and that comment says "strips the symbols and build-path strings". OBSERVED. So a non-stripped binary can contain build-path strings. Whether the game binary does, and whether it depends on the output directory, is UNVERIFIED.
- The object and source paths appear in the compiler argv (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:83`, `:85`). Whether they reach the binary without `-g` is UNVERIFIED.
- Timestamps. gcc does not embed a build timestamp by default. PREDICTED. UNVERIFIED for these flags and this gcc.

Experiment required before any tier-2 claim (run on one machine first, then two): build the same source twice into the same directory and into two different directories; compare binary hashes; then run on a second machine with the same compiler version. Record the results in this document.

### 4.4 What is not guaranteed, even at tier 1

- Runtime behavior of a standard artifact. It reads its input at run time (`src/PSXRecomp.Cli/RecompileCommand.cs:99`), so the same binary can behave differently with a different input file. CONFIRMED from the comment; behavior PREDICTED.
- The runtime host. `dotnet publish` output is not in any identity (Section 2.5). Whether it is reproducible is UNVERIFIED.
- Behavior across OS and compiler versions. Not guaranteed. The CI uses the runner's gcc (2.7).
- Builds across C library, import library, header, specs, or driver configuration changes (Section 3.7). These are accepted limits, and the manifest does not record them.
- Any build whose working directory or `PATH` resolves a different compiler (Section 3.7).
- Confidentiality of the output directory. It holds game-derived code and data (2.3, 3.5). This design does not make it safe to share. It stays under the same rules as before.
- Any run that uses an external BIOS (`src/PSXRecomp.Core/Recompiler/RecompiledArtifactCodeGen.cs:629`). The BIOS is never part of the artifact, so the BIOS file is outside the guarantee. Only its provenance label is recorded (`src/PSXRecomp.Infrastructure/Standalone/RuntimeHostManifest.cs:60-68` labels such as `user-supplied`). The BIOS content is never recorded, hashed into a committed file, or included in a manifest.
- Artifacts built with `guardStats` or `traceUnits`. These are measurement builds. They are not release builds, and the manifest must say so.

## 5. Build history

**Status.** Required design. No history log exists at this SHA.

Proposed: an append-only local log, one JSON object per build, with the timestamp, compiler path, step outcomes, the `buildKey`, and the presence-reported environment names. It is local-only and is never committed, consistent with `docs/development/artifact-policy.md:72-73`. Its location depends on #42 (Project / Workspace), which is not implemented. Until then, the log lives beside the output directory and outside it: a sibling file in the parent directory, named `<outputDirName>.build-history.jsonl`. It must not be inside the output directory. The pre-check of 3.8 step 0 refuses any non-empty output directory, so a history file inside it would refuse every re-run. It is a diagnostic record. Nothing reads it to decide whether to build.

For every build attempt that passes the pre-check, the packaging caller (Section 7.2, step 6) builds one `BuildHistoryEntry` (Domain, `[Domain]`) and passes it to `IBuildHistoryLog.Append`, whatever the outcome: success, or a failure at the probe, the build, or the commit. A failure is therefore recorded at the point it occurs, not only after a commit. A refusal by the pre-check (3.8 step 0) appends nothing, because that refusal writes nothing. An I/O exception raised by `IsEmptyOrAbsent` (step 0), or by the probe's own I/O, is not a classified refusal. It is recorded as `PackagingStepFailed` with `FailedStep` `preflight`. An I/O error in the probe is recorded as `PackagingStepFailed` with `FailedStep` `probe`; `ToolchainUnavailable` is only for a missing toolchain. So every packaging step has an outcome. The schema covers every outcome. `Outcome` is one of `Succeeded`, `ToolchainUnavailable` (7.2 step 1, a missing toolchain only), `BuildFailed` (7.2 step 3, the build), `PackagingStepFailed` (defined once here: every non-refusal failure that is neither a build failure nor a commit failure, with `FailedStep` naming the step: `preflight` (7.2 step 0, an I/O exception from `IsEmptyOrAbsent`), `probe` (7.2 step 1, an I/O or start failure after the toolchain was found), `staging` (7.2 step 3, a `CreateStaging` failure), `hash` (7.2 step 4, a source or binary `Sha256` failure), and the write-order steps of 3.8: `runtimeProvisioning` (3.8 step 2), `sidecar` (3.8 step 3), `runtimeHostJson` (3.8 step 4), `readme` (3.8 step 5), `digestH3H2` (3.8 step 6), and `carrierWrite` (3.8 step 7)), or `CommitRefused` (7.2 step 5, the commit: a non-empty target at commit time, a failed `RemoveEmptyDirectory`, or a failed no-replace move). Each step number is labelled 7.2 or 3.8 where it is used. `FailedStep` names the failing step, for example `sidecar` or `carrierWrite` (null on success). `BuildKey` and `Steps` are nullable when the failure occurs before they exist (for example, `BuildKey` before the probe completes). The entry carries the real paths as data: the compiler executable, the output directory, and the staging directory. The entry has no time field, because Domain forbids `DateTime.Now` and `DateTime.UtcNow` (`src/architecture.contract.json:25-26`; matrix Forbidden API table). The Infrastructure adapter adds only the timestamp when it writes the line. It does not add or change any other field.

Open: whether history is per-output-directory or per-project. See Section 9.

## 6. Clean and verify (no Skip in v1)

**Status.** The clean, verify, and build-coverage behaviour below is required, not current code. The workflow and the clean command do not exist at this SHA.

**Build always runs.** In v1 the workflow must run the build on every request. There is no Skip path, and no record, hash, or environment check can cause a build to be skipped. A future Skip needs a separate design. That design must fingerprint every file the driver resolves, including the C runtime, import libraries, headers, specs, driver configuration, and the compiler binary, and it must be reviewed on its own. This document does not define it.

- **Clean.** The workflow and the build commit never call `IBuildArtifactStore.Remove`. Clean's ownership of an output directory rests only on the carrier's per-file digests and bare names. This is a residual risk (Section 9, item 25), not an ownership check that exists: the W12 ownership check (section 11, Q18, line 511) covers the H2 private copy, and this design does not extend it to output directories. Before removing any file, Clean requires that the file's SHA-256 equals the digest the carrier records for it (`source.sha256`, `binary.sha256`, `object.sha256`, or `packaged.imageSidecar.sha256`). `build-manifest.json` has no digest in the carrier, so it is removed by its bare name under the containment check only. No new schema key is added. The carrier is unsigned (3.9), so a forged carrier that records a file's own digest passes these checks; that residual risk is Section 9, item 25. Owner: Issue C for Clean. Requirement, not implemented, not run (P-17). Clean also applies the containment check: each bare name is resolved under its base directory before removal. If the check fails, Clean refuses. Every name in the carrier must be a bare file name: no path separator (`/` or `\`), no `..`, no drive qualifier, and not rooted. Clean resolves each name under the output directory and refuses the whole Clean if any name is not bare or resolves outside that directory, so nothing is removed. The carrier is unsigned (3.9), so this check applies even though the tool wrote the carrier. The containment and ownership rule is W12's requirement (W12 at `a6027a2`, section 11, Q18, line 511). It removes exactly the files the carrier names: `source.file`, `binary.file`, `object.file` (when present), `packaged.imageSidecar.file` (HLE), and `build-manifest.json` (packaged) (Section 3.5). Base directories: `source.file`, `binary.file`, and `object.file` are bare names under `<outputDir>`. `packaged.imageSidecar.file` (`artifact-image.bin`) and `build-manifest.json` are bare names under `<outputDir>/runtime/`, which is the base of the sidecar in the schema (3.5). Clean calls `Remove` once per base directory (7.2), and HLE Clean resolves every carrier file this way. Clean runs in the caller through `IBuildArtifactStore.Remove` (7.2). `build-manifest.json` is removed as well. It is named explicitly and not hashed, because it cannot list its own hash. The caller writes it into the staging area as the last file before the commit (Section 7.2). For a packaged build the same rule applies to `runtime/build-manifest.json`, and clean removes that one file only. It never removes any other `runtime/` file, because the rest of the packaged layout is W12 Q13's concern. A file not in that list, and not the manifest, is never deleted. `artifact-input.txt` and the engine's `artifact-image.bin`, written directly under the output directory and not under `runtime/`, are not in the list. The sidecar `runtime/artifact-image.bin` (`packaged.imageSidecar.file`) is in the list. The engine writes them (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:511-512`), and the engine is not migrated to the workflow (Section 7.2), so clean does not touch them. Their removal belongs to the engine migration. Clean does not make the directory reusable. `runtime-host.json`, the README, the runtime host binary, and any file the carrier does not name remain, so the directory stays non-empty, and a re-run into the same path is refused with `OUTPUT_DIRECTORY_NOT_EMPTY` (3.8, step 0). The operator must remove the directory or choose a new path.
- **Verify.** Re-hash the file named by each of these keys, and compare it with that key's `sha256`: `source`, `binary`, `object` (when present), and `packaged.imageSidecar` (HLE). H3 is therefore checked by Verify as well as by the packaged host at launch (Issue B). `runtimeInputs` entries are not verified by Verify in Issue A. An `environment` entry names a variable and has no file. An `exe` or `chd` entry (standard artifact, Issue D) names the caller's input file, which is outside the package, so Verify cannot read it. Its check belongs to Issue D, with the input identity of 3.1. The carrier's own `build-manifest.json` has no digest, because it cannot list its own hash, so Verify does not check it. This is a check that the output has not been changed since the build. It is not a build decision, and it must never prevent a build. A mismatch must be reported. It must not be repaired by editing the manifest.

**Extra arguments.** The manifest records extra arguments as given. Each build with an extra argument runs like any other build. Relative tokens such as `-Iinclude` resolve against the working directory, which is not keyed. That is an accepted limit (3.7). Release builds keep the working directory fixed.

**Build coverage.** The workflow's cost before the build (load, lowering, and codegen) runs on every request, as does the build itself. For a CHD input, the load also runs the disc analysis (`src/PSXRecomp.Cli/CliInput.cs:115`, `RomAnalysisPipeline.RunFromChd`). ## 7. Management layer that keeps the Build API

The goal is that every current caller compiles and behaves the same, and the new workflow sits above the port. The layer rules are ADR-017 points 1-3 (Domain owns ports; Infrastructure owns file, process, and clock I/O; Application does not depend on Infrastructure except at one composition-root site) and matrix rule 3 (`docs/architecture-matrix.md:66`: Application does not acquire host resources directly).

### 7.1 Keep the port

- `IGeneratedHostBuildService`, `GeneratedHostBuildRequest`, and `GeneratedHostBuildResult` (`src/PSXRecomp.Core/Recompiler/GeneratedHostBuild.cs:48`, `:63`, `:86`) keep their current members. Any new request field is optional and goes at the end of the positional record, so every existing call site still compiles. The existing callers listed in 2.1 are not edited by this design.
- The result keeps its shape. Build provenance is gathered by the layer above, not returned through the port.

### 7.2 Domain ports, the workflow, and the composition root

**Status.** This section and sections 7.3 and 7.4 describe the required ports, records, and ownership. None of them exists at this SHA (see the status note at the start of section 3). `TOOLCHAIN_UNAVAILABLE` already exists (`src/PSXRecomp.Cli/DoctorCommand.cs:66`, `src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:157`), and the workflow's use of it is new code that reuses that name.

**Why the workflow lives in Domain (PSXRecomp.Core).** `PSXRecomp.Cli` is classified as Infrastructure, because its namespace is `PSXRecomp.Infrastructure.Cli` (`src/PSXRecomp.Cli/RecompileCommand.cs:7`, Infrastructure namespace root in `src/architecture.contract.json:5`). **Layer declaration.** The contract requires a layer declaration (`src/architecture.contract.json:58`, `"required": true`). Every new Domain type and port in this section carries `[Domain]`, as `src/PSXRecomp.Core/Recompiler/GeneratedHostBuild.cs:47` does for the existing port. The new types live in `PSXRecomp.Core` and use no host call, no `DateTime`, and no `Guid`.

It is produced by one pure Domain function, `BuildCodegenRecord.From(CodegenOptions options, CodegenInputs inputs)`, which hashes each array with SHA-256 over its little-endian bytes. The workflow calls it once, before the key is computed.
- `BuildStagingArea`: fields `DirectoryPath` (string) and `RunToken` (string; 128 bits of randomness from a cryptographic random source, generated by `CreateStaging`). A handle whose token is absent from the table, including a forged handle with an arbitrary path, is refused and deletes nothing (P-10). `Commit` removes the handle's `RunToken` from that table when it succeeds, so a handle copied or kept after the commit is refused by `Discard`.
- `BuildHistoryEntry`. It is string-only, except for an ordered list of strings. It has these fields: `BuildKey` (nullable before the probe completes), `Outcome` (`Succeeded`, `ToolchainUnavailable`, `BuildFailed`, `PackagingStepFailed`, or `CommitRefused`), `FailedStep` (nullable; null on success), `DiscardFailed` (boolean; true when `Discard` failed after the primary failure, and the primary `Outcome` and `FailedStep` stay unchanged), `CompilerExecutable` (a real local path), `OutputDirectory` (real), `StagingDirectory` (real), `ProductRevision`, `PresentEnvironmentNames` (local only, a list of strings), and `Steps` (each element `"<step> <outcome> <exitCode>"`). It has no time field and no `FileInfo`, `DirectoryInfo`, or `DateTime` member.
- `ToolchainIdentity(bool Available, string? DriverVersionLine, string? LinkerVersionLine, string? TargetTriple, IReadOnlyList<string> PresentEnvironmentNames)`. The probe is in Infrastructure, because reading the environment is a host call (`Environment` is forbidden in Domain, `src/architecture.contract.json:22`). Only the names of the variables that are set are returned. Values are never returned.
  - Probe classification rule (requirement; the Windows error-code behaviour is UNVERIFIED, because this document cannot run a Windows launch). `Available = false` means the toolchain was not found: before the launch, the probe looks up the executable explicitly in exactly the directories the launch resolves, in the same order. On Windows that is the working directory first, then each directory in `PATH`, with each `PATHEXT` extension tried. On POSIX it is each directory in `PATH`. The probe then launches the path the lookup returned, so the lookup and the launch cannot resolve different files. That the lookup matches the launch resolution is UNVERIFIED on Windows and on the Linux CI platform. If no candidate exists, `Available` is false. The probe also records the Win32 error code of the launch (on Windows, `ERROR_FILE_NOT_FOUND` or `ERROR_PATH_NOT_FOUND`; UNVERIFIED). Any other start failure (a candidate exists but cannot be started, for example an existing non-executable file or a permission-denied start) is not `Available` false: it is `PackagingStepFailed` with `FailedStep` `probe`. Today's adapter (`src/PSXRecomp.Infrastructure/GeneratedHostBuildService.cs:261-266` at `2e3ecad`) catches every `Win32Exception` from `Process.Start` and returns `ToolchainOutcome.Unavailable`, which `ToFailure` maps to `TOOLCHAIN_UNAVAILABLE` (`:155-158`). This design changes that for non-not-found failures. The change is a stated design decision, not a preserved behaviour, and it needs an adapter change (Issue C). Tests P-13 to P-15 (Section 10) cover the three cases. The workflow then fails before any staging area is created, with `TOOLCHAIN_UNAVAILABLE`, and the history outcome is `ToolchainUnavailable`.

It fails, and deletes nothing, if the directory has entries. It is the only removal used by the commit rule (3.8, step 2). Proposed, owner Issue A (#864).
  - `void Discard(BuildStagingArea area)`: removes only the staging directory that the run created. The `BuildStagingArea` carries the `RunToken` of its record (see above). `Discard` looks the token up in the store's own table of runs it created and removes only the directory that table records. A token that is not in the table (a forged or stale handle) is refused, and nothing is deleted. It removes entries bottom-up: each entry is deleted with a non-recursive delete after its children are gone, and every path is checked to resolve under the recorded staging directory before deletion (the containment check of Clean, 6). It refuses to follow a reparse point. It never runs on the output directory. Discard is the only recursive removal the design allows: it removes the staging tree this tool created, and nothing outside the staging area (containment-checked; requirement, not implemented, not run, P-18). A failure is recorded in the history entry's secondary field `DiscardFailed` (Section 5), not ignored, and the primary outcome is unchanged. Called on failure only, never after a successful commit. Proposed, owner Issue A (#864).

It validates each name as a bare file name and resolves it under `baseDirectory`, and it refuses the whole call if any name is not bare or escapes that directory. Proposed, Issue C. It is a port method because Domain may not call `System.IO.File` (`src/architecture.contract.json:20`).

1. Resolve `compiler = request.CompilerExecutable ?? GccGeneratedHostRecipe.DefaultCompiler` once. ## 8. Recommendation

1. Issue A first (3.9): write the carrier `build-manifest.json` (schema 1) with the H2 and H3 digests and the caller-supplied record fields, every packaged file staged before one commit (3.8). Issue C then computes the build key, the codegen records, and the toolchain values, and runs the workflow (7.4). Gated: Issue A may be implemented and reviewed with fixture-based tests, but it does not enable production carriers until the W12 reader implements Q19 option (a) and the Section 10 fixture tests pass (3.10, 7.4). The gated part of Issue A (criteria (a), (b), (i), and (j)) follows Q8 option (i) (section 9, item 8), and is unblocked only after implementation verifies non-destructive behaviour. Do not change generated C. Record and verify; make no stability promise.
2. Record codegen options and the generator version in the build key. This closes the largest gap (2.4).
3. Add a `Stdout` field to `ToolchainResult` (3.4). Capture the compiler `--version` and target through `IToolchainProbe`, implemented in Infrastructure. Do not record local paths in the manifest.
4. Keep Build always-on in v1 (Section 6). Treat any future Skip as a separate design with a file fingerprint.
5. Keep the existing Build API. Place the workflow in Domain over `IBuildArtifactStore`, `IToolchainProbe`, `IBuildHistoryLog`, and `IGeneratedHostBuildServiceFactory` (which yields `IGeneratedHostBuildService`). Infrastructure implements the ports, and `PSXRecomp.Cli` composes them. Migrate in this order: Issue A (carrier writer and HLE staging, without the workflow), then Issue C (workflow, ports, and the migration of the packaging callers), then Issue D (`RecompileCommand`, non-packaged carrier). Section 7.4 gives the ownership; it is an owner decision.
6. Keep history local-only and wait for #42 to decide its location. Run the tier-2 experiment (4.3) before any binary-identity claim.

This sequence respects the issue's priority: it does not block the vertical slice, and it does not change the artifact bytes that the existing tests depend on.

This design adopts the W12 method as the proposed method, taken from W12 section 3.4 (steps 1 to 5), with the release point option (ii) (below):
    1. The host creates a private directory for the run, with an unpredictable name and an access control list that gives write and delete rights only to the running user. The target platform is Windows. The directory is outside the distribution.
    2. The host reads the original artifact once into a buffer, and writes that buffer to the private copy, created with create-new so that an existing file is an error.
    3. The host opens the copy for reading with sharing `FileShare.Read` only, and computes the SHA-256 over the bytes read through that handle. The value must equal `binary.sha256`. The release point of the handle is option (ii), below.
    4. The host launches the copy by its path while the handle is still open.
    5. The host never launches the original path. Deletion is conditional: D-a, provisionally adopted, owner to confirm (W12 Q18 at `a6027a2`, line 511; see below). Earlier wording of this document said the directory is deleted after the run, or on failure, without condition; that wording is withdrawn.
    W12 rejects two alternatives, which W12 labels (R1) and (R2) at `a6027a2`, section 11, line 511: a handle on the original file (process creation takes a path), and launching the original after hashing (the file can be replaced between the hash and the launch).
    **Release point: ruled option (ii) (W12 Q18, 2026-10-30).** The two options below are kept for the record. Option (i) is not taken.
- (i) Hold the handle until process creation. This is the wording of this document's earlier revision, recorded once here. Process creation is `Process.Start` at `src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:1352`, inside `RunProcess` (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:1310`), which the `RunSegment` call at `:857` invokes. `RunSegment` starts at `:723`. Option (i) needs a creation signal to the host, which is not designed.
- (ii) Hold the handle until the `RunSegment` call that launches the copy has returned. W12 rules this at `a6027a2` (section 3.4, step 3, and section 11, Q18, line 511). Under option (ii) the host does not need to detect process creation. W12 also records that option (ii) does not make the child's exit visible: on a timeout the engine does not wait for the child (W12 at `a6027a2`, section 11, Q18 timeout facts, line 513). Branch selection (CONFIRMED at `2e3ecad`): `src/PSXRecomp.RuntimeHost/Program.cs:268` sets `needsBridge = !manifest.GuestFirmware`; `:284-286` select `HostTransfer` mode when `needsBridge` and `RuntimeHost` mode otherwise; `:292` passes `biosRuntimeFactory: needsBridge ? BiosRuntime : null`. So an HLE package (`GuestFirmware` false) runs in `HostTransfer` mode with a BIOS runtime factory, and a firmware package (`GuestFirmware` true) runs in `RuntimeHost` mode with a null factory. The engine creates a bridge object unless both the factory is null and `_guestFirmware` is false (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:782`). Firmware therefore still gets a bridge object. Neither packaged kind reaches the bridge-less `RunProcess` branch (`:1360`, kill at `:1368`). The bridge kill sites are `:1430` (the pump faulted), `:1453` (the pump has not completed) and `:1472` (the pump ended and the child has not exited). Both branches return without waiting for the child's exit. The kill and exit facts are W12's (section 11, Q18 timeout facts, line 513) and stay UNVERIFIED where W12 marks them so, including `Process.Kill(true)` on this platform. `ForPrebuiltArtifact` (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:628`) only constructs the engine and does not launch it.

**Deletion: D-a provisionally adopted, owner to confirm (W12 Q18, options D-a and D-b).** Earlier wording of this document says the private directory is deleted after the run, or on failure, without condition. W12 at `a6027a2` makes deletion conditional, and names two options. **Owner ruling (2026-10-30): D-a, adopted provisionally; owner to confirm.** These are the normative rules, mirroring W12 at `a6027a2` (section 3.4, step 5, and section 11, Q18):
- (D-a, provisionally adopted; owner to confirm.) The host may delete the private copy only after a public result confirms that the child process and its residual processes have exited.
- W12 requirement (`a6027a2`, section 11, Q18, line 511): before any deletion, the canonical path containment and ownership of the private copy and its directory are checked. This check is a precondition of the deletion, in addition to the exit confirmation.
- If exit is unconfirmed, the host does not delete. It reports the directory as residual, with its path.
- A timeout or a kill request alone does not prove that the child has exited. W12 at `a6027a2`, section 11, Q18 (line 511) and its timeout facts (line 513), record this.
- Deletion is limited to the one private copy the host created. There is no blanket recursive deletion. A failed deletion is reported as residual, not ignored.
- (D-a, provisionally adopted; owner to confirm.) D-a needs an exit-confirmation result that the host can read. None exists today: `LastStopDiagnostics` is internal (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:222`). The public API is a prerequisite. It is not designed here, and the owner must approve it.

**Owner to confirm: conflict on the deletion option.** Three sources bear on cleanup. (1) The Issue #46 comment of 2026-10-30 records D-b (no deletion during the run). (2) The Issue #48 and Issue #865 comments of 2026-10-30 record D-b (separate cleanup only after positive exit evidence). This worker did not read those comments; the owner's brief quotes them, and W12 at `a6027a2` (section 11, Q18, line 512) names them. (3) The owner's instruction of 2026-10-30 adopts D-a. This document adopts D-a, as written above, and does not silently choose D-b. The owner must confirm which option applies. If D-b is confirmed, this item, 3.9 Issue B (f), and W12 Q18 change together.
- (D-a; provisionally adopted; owner to confirm) The host deletes only the one private copy it created, and only after the exit-confirmation result reports that the child exited and that no residual process remains. The removal is the containment-checked removal of that copy alone (Issue B (f)): never a directory tree, and never a file the host did not create (F6). The W12 containment and ownership checks (section 11, Q18, line 511) must also pass before any deletion. Any other outcome leaves the copy in place. After a confirmed exit, the empty private directory is also removed, by the same non-recursive, containment-checked removal; if that removal fails, the directory is reported as a residual directory with its path. Requirement, not implemented, not run (P-16). W12 (`a6027a2`, section 11, line 513) says that on a timeout the engine does not wait for the child to exit, that `LastStopDiagnostics` is `internal`, and that D-a therefore needs a public exit-confirmation result. D-a is therefore available only if the owner accepts a new public exit-confirmation API, which does not exist. The engine's `LastStopDiagnostics` is internal (`src/PSXRecomp.Infrastructure/RecompiledHostExecutionEngine.cs:222`).
- (D-b) The host never deletes the directory during the run. It leaves the directory in place, reports it as a residual with its path in the run result, and a later cleanup step removes it (`docs/design/issue-48-runtime-config.md` at `a6027a2`, section 3.4, step 5 and section 11, Q18). That later cleanup is a separate step outside the run. It deletes only after positive exit evidence for the child and its descendants, and after the containment and ownership checks (W12 at `a6027a2`, section 11, Q18, line 512). Without that evidence it deletes nothing.

**Owner ruling (2026-10-30): release option (ii).** The handle is held until the `RunSegment` call that launches the copy has returned. Deletion is set out below. Either way the engine does not open the path itself. The POSIX equivalent is UNVERIFIED (W12 section 3.4). The owner must confirm the directory access rules, the sharing rule, and the deletion option (D-a or D-b). The release point is recorded in both documents.

The owner should confirm that W12's enumeration matches the key list in 3.5.

The Q8 (i) ruling covers packaged builds only. Until the owner answers, these paths are unchanged and no document claims otherwise.
21. **Re-run consequence of the Q8 (i) pre-check (owner question).** A re-run into the same packaged output path now needs the operator to remove the old output directory, or to choose a new path. Does the owner accept this behaviour change for `PackageCommand` and `FirmwareDistribution`? This is the consequence recorded in 3.8 step 0. Clean does not make the directory reusable (Section 6): after Clean the directory still holds the files the carrier does not name, so the operator must remove the directory or choose a new path.
22. **Failed attempts in the history (owner question).** This design records every attempt that passes the pre-check, including failures (Section 5). Should pre-check refusals be recorded as well? This design says no, because a refusal writes nothing.

23. **`CommitStaging` after this design (owner question).** `CommitStaging` (`src/PSXRecomp.Infrastructure/Standalone/FirmwareDistribution.cs:518-530` and `:542` at `2e3ecad`) is the swap the firmware packaged commit (`:487`) uses today. This design requires the commit-time guard to replace it for that commit before criterion (b) can pass. Owner question: after replacement, should `CommitStaging` be kept for non-packaged uses, or replaced for every caller? Until the replacement is implemented, the firmware packaged commit keeps using the swap, and criterion (b) cannot pass.

24. **Unverified no-replace move (owner question).** The safety of the commit between the recheck (1) and the move (3) rests on a move that refuses an existing destination. Nothing in the repository checks this on Windows, and it is UNVERIFIED on POSIX. Until it is verified, the guard is unproven, and no packaged commit (criteria (a), (b), (i), (j)) may be enabled. Does the owner accept that verification as a gate?

25. **Forged carrier (owner question; residual risk).** The carrier is unsigned. Clean's per-file digest check and its bare-name and containment checks (Section 6) stop a user file that a carrier names with a digest that does not match it, but a forged carrier that records the file's own digest is internally consistent and passes these checks, so it can still make Clean remove files the forger chose inside the output directory. Accept this as a residual risk, or require signing or a protected location?

## 10. Required test plan (planning only; nothing run)

**Status.** Every test in this section is a requirement. Each is labelled **not implemented, not run**. No test was written or run, and no criterion has passed. Windows ACL and sharing behaviour, and the POSIX equivalents, are UNVERIFIED until these tests run. Writer-to-reader fixtures (group G) are required before any production carrier is enabled (3.10).

**A. Fail-closed behaviour (host and game window, Issue B).** Each case is one test, and the host and the game window (H15) must give the same result.
- A1. Carrier missing: classified setup failure, no guest code runs. **not implemented, not run**
- A2. Carrier unreadable (for example, locked): classified setup failure. **not implemented, not run**
- A3. Carrier JSON does not parse: classified setup failure. **not implemented, not run**
- A4. H2 or H3 missing or unreadable: classified setup failure. **not implemented, not run**
- A5. H2 digest mismatch, and H3 digest mismatch, tested separately: refused. **not implemented, not run**
- A6. Firmware carrier with a `packaged` block, and HLE carrier without one: refused. **not implemented, not run**
- A7. No warning-only mode exists, and verification cannot be switched off. **not implemented, not run**

**B. TOCTOU (replacement between hash and use).**
- B1. Digest H3: replace `artifact-image.bin` after its hash and before use. The run is refused, or the array that was hashed is the array from which the image words are built (reference equality through the W12 seam). **not implemented, not run**
- B2. Digest H2: replace the original artifact after its hash. The launched path is the private copy, and the launched bytes equal the hashed bytes. **not implemented, not run**
- B3. A second process under a different principal attempts to write and to delete the private copy while the handle is held. Both attempts are refused (W12 acceptance 11). **not implemented, not run**; Windows ACL and sharing UNVERIFIED.
- B4. The private directory and copy names are unpredictable, and create-new refuses a pre-existing directory or file (W12 acceptance 12). **not implemented, not run**
- B5. The original path is never passed to `ForPrebuiltArtifact` at the three launch sites: the main host, H15, and the firmware run. **not implemented, not run**

**C. Nullable keys (exact list only).**
- C1. Each key in the 3.5 nullable list is accepted when it is `null`. **not implemented, not run**
- C2. Each key outside that list is refused when it is `null`. Examples: `schemaVersion`, `binaryName`, `binary.sha256`, `binary.file`, `source.sha256`, `input.kind`, `codegen.mode`, `packaged`, `object`, `runtimeInputs`. **not implemented, not run**
- C3. A non-null nullable value with the wrong type is refused. An ordinary string for `toolchain.compilerVersionLine` and an array for `toolchain.recipeTokens` are accepted. **not implemented, not run**
- C4. A non-null digest that is not 64 lowercase hexadecimal characters is refused, including uppercase hex, for each digest field in the 3.10 rule 5 list (including `loadedCode[].sourceSha256`). **not implemented, not run**
- C5. The writer emits every v1 key, with `null` where a key is nullable and has no value. No key is omitted. **not implemented, not run**

**D. Missing key.**
- D1. For each required key in each carrier kind (HLE, firmware), its absence is refused. **not implemented, not run**
- D2. A nullable key that is absent, rather than present with `null`, is refused. **not implemented, not run**

**E. Unknown key at every level.** One test per level: top level, `input`, `codegen`, `source`, `binary`, `object`, `toolchain`, `packaged`, `packaged.imageSidecar`, `extraArguments`, a `runtimeInputs` entry, and a `loadedCode` entry. Each unknown key is refused. **not implemented, not run**

**F. Abnormal child exit (provisional: D-a, release option (ii)).** D-a is provisionally adopted; owner to confirm; it conflicts with the recorded D-b (see §0.1, and the owner-to-confirm note in 9 item 18). F1 to F6 are written on the D-a basis.
- F1. The child exits non-zero or crashes, and the public result confirms the exit. After the canonical path containment and ownership checks pass (W12 requirement, `a6027a2` section 11, Q18, line 511), the private copy is deleted by the containment-checked removal, and then the empty private directory is removed by the same non-recursive removal. Reporting: the copy and the directory are reported as removed when each removal succeeds. If either removal fails, that object is reported as a residual with its path, and nothing else is deleted. **not implemented, not run**
- F2. A timeout with a kill request, and the child still alive. Exit is unconfirmed, so nothing is deleted, and the directory is reported residual with its path. **not implemented, not run**
- F3. A kill request returns, but exit is not observed. Nothing is deleted. **not implemented, not run**
- F4. The parent exits, and a descendant process is still alive. Nothing is deleted, and the residual is reported. **not implemented, not run**
- F5. Deletion fails, for example because the file is locked. The failure is reported as residual, not ignored. **not implemented, not run**
- F6. An extra file that the host did not create is placed in the private directory. It survives, and no recursive deletion removes it. **not implemented, not run**

**G. Writer-to-reader fixtures (required before production carriers are enabled).**
- G1. An HLE package written by `ArtifactBuildManifestWriter` is read back by the W12 strict reader, and the digests match the written files. **not implemented, not run**
- G2. A firmware package written the same way is read back, with `binary.sha256` and no `packaged` block. **not implemented, not run**
- G3. Both fixtures include every v1 key, with the nullable keys set to `null`, so the Q19 rules are exercised end to end. **not implemented, not run**
